# 외부 빌드 웹 503 재점검

최신 결과: [외부 빌드 웹 로그인 복구](kiki-build-web-port80-restored-20261025.ko.md). 승인한 80 → 8092 OS 포트 매핑으로 외부 로그인 화면을 복구했다. 아래는 그 전 단계의 진단 기록이며 직접 8092 경로는 별도로 남아 있다.

## 19:35 KST 추가 확인: Apache 80번의 새 도메인은 정상

사용자가 별도로 설치·실행한 Apache와 80번 보안그룹 규칙을 확인했다. 사용자가 실제 테스트한 주소는 기존 `kios-build`가 아닌 `https://cloud-7-3b778824-09936d.lab.terminal-lab.kr/`다.

`/var/www/html`이 비어 있어 서버 직접 요청은 처음에 403이었다. 기존 파일이 없는 것을 확인한 뒤 독점 생성 방식으로 `/var/www/html/index.html`에 비밀 정보 없는 점검 페이지를 추가했다. 기존 파일은 덮어쓰지 않았고 Apache를 재시작하지 않았다. 새 파일 SHA-256은 `193e5401c5aa0b8c70b560e28de5cf9fa0428055d0be043ba2f6c6e96ccbef85`다.

이후 VM의 80번과 **새 도메인의 외부 HTTP·HTTPS 모두 200**, 본문도 실제 Apache 점검 페이지와 일치했다. 브라우저에서도 표시를 확인했다. VM 패킷에는 `10.0.161.214 → 10.250.254.229:80` 연결과 응답이 관찰됐다. 따라서 관리형 프록시·빌드 VM 사이 모든 연결이 실패한다고 일반화할 수 없다. 기존 `kios-build → 8092`의 503과 새 도메인 80번의 정상 응답은 구분해야 한다.

아래 내용은 19:02 KST까지의 기존 도메인 점검 기록이다.

### 8092의 자동 발급 주소 비교

19:37 KST, 같은 VM의 8092에 자동 주소 `cloud-7-3b778824-757ae0.lab.terminal-lab.kr`를 연결해 `/healthz`를 검사했다. 이 주소도 약 20초 후 503을 반환했다. 따라서 기존 `kios-build` 이름에만 국한된 문제라는 가설은 지지되지 않는다. 80번은 정상이고 8092는 실패한다는 포트별 차이를 플랫폼 측 backend·네트워크 진단에 반영해야 한다. 8092 실패가 애플리케이션 자체 문제인지 앞단 경로 문제인지 판단할 때는 앞선 VM 직접 200과 패킷 관찰 결과를 함께 사용한다.

비교용 주소의 연결 해제는 사용자 확인창 클릭 후 완료됐다. VM의 외부 연결 목록에서 비교용 주소가 사라지고 원래 `kios-build → 8092`와 사용자가 만든 `cloud-7-3b778824-09936d → 80` 두 연결이 유지되는 것을 확인했다. 빌드·인증 컨테이너와 원본 산출물은 그대로 유지했다.

2026-10-25 19:02 KST 기준 외부 로그인 연결은 **미복구** 상태다. 서버 내부의 로그인 200 응답을 외부 접속 성공으로 판단하지 않는다.

## 적용 및 확인

- 프로젝트: `custom-lab-user-7`.
- VM: `build-server`, `3b778824-515a-4955-a8a1-4acae7629384`.
- 기본 인터페이스: `net-infra`, `10.250.254.229`, `fa:16:3e:f3:ef:2e`.
- 도메인: `kios-build.lab.terminal-lab.kr`.
- 기존 연결을 해제한 뒤 동일한 도메인을 동일 VM의 **HTTP 8092**에 다시 등록했다. 18:53:39 해제와 18:54:03 등록 작업 모두 플랫폼 작업 이력에서 완료를 확인했다.
- VM에 연결된 보안그룹은 `kiki-build-web-20261025` 하나다. TCP 22는 `10.0.161.214/32`, TCP 8092는 기존의 `0.0.0.0/0` 수신 규칙이며 IPv4 송신은 허용된다. 이번 점검에서 접근 범위를 확대하지 않았다.
- 같은 보안그룹을 다시 연결하기 위한 해제 요청은 플랫폼의 “인스턴스에는 보안그룹이 하나 이상 필요합니다” 제약으로 거절됐다. 그룹은 계속 연결돼 있으며 재적용이 성공했다고 표시하지 않는다. 다른 VM·그룹은 변경하지 않았다.
- 웹 앱 코드, 컨테이너, 인증 DB, SSH 포워딩은 변경하거나 재시작하지 않았다.

## 검증 결과

| 검사 | 결과 |
|---|---|
| VM 직접 HTTP, 공개 Host, `/login` | 200, Secure 쿠키 |
| VM 직접 `/`, `/healthz` | 200 |
| VM 직접 미인증 `/api/jobs` | 401 |
| 도메인 재등록 후 공개 HTTPS `/login` | 약 20초 후 503 |
| 기존 공개 HTTP 탭 | 503 화면 확인 |
| 같은 시간 ens3 패킷 관찰 | SSH SYN 3개 관찰, 8092 패킷 행 0개 |
| 캡처 종료 통계 | captured 3 / received by filter 5 / dropped 0 |

캡처는 즉시 출력 모드로 수행했고 패킷 본문은 저장하지 않았다. SSH 비교 연결이 관찰되므로 캡처 인터페이스 자체는 동작한다. 다만 이 결과만으로 관리형 프록시의 backend 미반영과 게스트 앞단의 Neutron 차단을 구별할 수는 없다. 사용자 콘솔에는 backend 런타임·연결 로그·Neutron 실제 적용 상태를 확인할 기능이 없어, 해당 플랫폼 운영 정보가 다음 확인에 필요하다. 빌드 VM에 별도 프록시 소프트웨어를 설치하는 것은 이 문제를 해결하지 않는다.
