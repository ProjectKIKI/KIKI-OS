# 한국어 빌드 웹과 OS 버전·CPU 대상 관리

## 사용 방법

릴리즈별 패키지 선택·ISO 연결·차이 비교·구성 잠금·보관은 [릴리즈 관리 운영 문서](kiki-build-web-release-management.ko.md)를 참고한다.

운영 주소는 [빌드 웹](https://cloud-7-3b778824-09936d.lab.terminal-lab.kr/)이다. 기존 관리자 계정으로 로그인한다.

1. **소스·바이너리 버전**에서 입력 패키지와 소스 SHA, 후보 스냅샷의 검증 범위를 확인한다.
2. **버전별 ISO**에서 OS 버전, 고정 패키지 스냅샷, GNOME 50/최소 systemd 구성, CPU 대상을 선택한다.
3. 생성한 작업에서 로그와 검증 결과를 확인한다. 완료 후 ISO, SHA-256, 검증 명세를 내려받는다.
4. OS 버전·CPU·작업 상태로 이력을 조회한다. 같은 입력의 재생성도 새 작업과 파일로 보존한다.

OS 버전은 커널 버전과 별개다. 예를 들어 `2026.10.25-r1` ISO가 Linux `6.1.187` 패키지를 사용할 수 있다. 기존 스냅샷과 ISO는 덮어쓰거나 새 이름으로 이동하지 않는다.

메뉴·폼·설명·상태·실행 계획은 한국어로 표시한다. 패키지 식별자, 명령, 파일 경로, 컴파일러 원본 로그는 유지한다. 운영 현황의 기존 빌드 경로 집계와 후보 보관소 집계는 표시 범위를 함께 안내한다.

## 버전과 입력 고정 규칙

- 보관 구조: `release-store/release-versions/<OS 버전>/manifest.json`.
- 명세 형식: `kiki-os-version-v2`. `targets` 아래 CPU 대상별 스냅샷 ID와 스냅샷 명세 SHA-256을 기록한다.
- 같은 OS 버전·CPU 대상에는 다른 스냅샷을 연결할 수 없다. 명세 파일 자체가 바뀌어도 거부한다. 새 패키지 구성에는 새 OS 버전을 사용한다.
- 향후 같은 OS 버전의 기존 x86_64, v3, v4 변형은 각자 고정 입력을 가진다. 서로 다른 CPU 패키지를 한 ISO에 섞지 않는다.
- 파일명: `kiki-<OS 버전>-<운영 구성>-<CPU 대상>-<작업 ID 앞 8자리>.iso`.
- ISO 루트의 `/etc/kiki/build-target.json`과 작업 결과에 OS 버전·스냅샷·CPU 대상·검증 분류를 기록한다.
- 과거 버전 명세와 OS 버전 필드가 없는 작업도 읽을 수 있다. 과거 작업은 스냅샷 이름을 버전 표시에 사용한다.

## CPU 대상의 현재 범위

| 대상 | 현재 동작 | 활성화 조건 |
|---|---|---|
| 기존 `x86_64` | 보존 패키지로 ISO 조립 가능 | x86_64 구성의 패키지 명세 확인 |
| `x86-64-v3` | 준비 상태·향후 옵션 표시, ISO 선택 비활성 | 해당 대상으로 빌드하고 런타임 검증한 패키지 스냅샷 확보 |
| `x86-64-v4` | 준비 상태·향후 옵션 표시, ISO 선택 비활성 | 해당 대상으로 빌드하고 런타임 검증한 패키지 스냅샷 확보 |

v3·v4는 Intel 제품 세대명이 아닌 x86-64 기능 등급이며 AMD에도 적용된다. [GCC 공식 설명](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html)을 기준으로 구분한다. 기존 패키지의 ISA 등급은 미분류로 표시하며, 기본 v1 호환이나 v3 최적화를 임의로 보증하지 않는다.

대상 명세는 `tools/ki2cpu.py`에서 관리한다. 아키텍처가 있는 모든 패키지의 `cpu_profile`이 선택 대상과 같아야 한다. 최적화 대상은 각 패키지에 `cpu_validation=runtime-verified`도 필요하다. `noarch`는 CPU 명세 일치 검사에서 제외한다. UI 비활성화 외에 서버에서도 검사하여 이름만 바꾼 v3·v4 ISO 요청을 거부한다.

화면의 C/C++·Rust·Go 옵션은 후속 컴파일 작업에 사용할 명세다. 이번 기능은 기존 바이너리를 최적화 대상으로 재컴파일하지 않는다. Rust 옵션은 [Rust 빌드 문서](https://rustc-dev-guide.rust-lang.org/building/optimized-build.html), Go의 `GOAMD64`는 [Go 공식 환경변수 설명](https://go.dev/doc/install/source#environment)을 참고한다.

후속 대상별 빌드에서는 CPU 등급·도구 체인·플래그·소스 잠금·의존 패키지 SHA를 캐시 키에 넣고, 패키지와 스냅샷을 분리해야 한다. 지정한 CPU 기능만 노출한 VM에서 런타임·설치·GDM/Wayland·GTK 실행을 검증한 뒤 대상 명세를 등록한다. 빌드 서버에서 실행됐다는 사실만으로 v3·v4를 승인하지 않는다.

## 운영과 배포

인증 이미지에는 `ki2ci_auth.py`와 한국어 모듈·번역 사전·브라우저 스크립트를 함께 포함한다. ISO 작업자는 격리 실행(`python -I -B`)에서도 자신의 읽기 전용 코드 디렉터리에서 CPU·화면 모듈을 찾는다.

현재 후보 배포 경로는 `/build-kikios/kiki-build/candidates/mesa-native-20261023/ui-versions-20261025-r1`이다. 최종 소스 잠금은 `stage-r4/source-lock.json`, 인증 이미지는 `localhost/kiki-build-auth:ko-versions-20261025-r4`이다. 기존 `release-code`는 보존하고 새 코드 경로를 사용자 systemd의 `kiki-release-worker.service.d/ui-versions.conf`로 선택한다. 인증 이미지 선택은 기존 `web-http.conf`에서 관리한다.

설정 변경 전 파일은 후보 배포 경로의 `before`에 보관한다. 계정·비밀번호와 인증 DB는 기존 상태 볼륨을 계속 사용하며 사본을 만들지 않는다. 컴파일러 컨테이너, 원본 설치기·KI2, 기존 보관 객체, 외부 80번 연결 방식은 유지한다. 코드 되돌림이 필요하면 작업 대기열이 비어 있는지 확인한 뒤 이전 이미지와 코드 경로로 설정을 복원하고 웹 서비스만 재시작한다. 생성한 버전과 산출물은 삭제하지 않는다.

ISO 완료는 입력 SHA·서명·의존성·파일 명세·ISO SHA·BIOS/UEFI 구조 검사 통과를 뜻한다. 실제 VM 설치·GDM 로그인·하드웨어 CPU 검증과 Secure Boot 서명은 각각 별도 결과로 표시한다.
