# 인증 웹 컨테이너 포트 매핑

현재 실행 구성은 [일반 HTTP 웹 서비스](kiki-build-web-http-20261025.ko.md)다. 외부 프록시 전용 기능을 제거했고, 호스트의 두 주소를 컨테이너의 동일한 HTTP 8092로 연결한다. 아래 8093 매핑 설명은 이전 배포 기록이다.

2026-10-25 인증 웹을 `localhost/kiki-build-auth:20261025` 전용 이미지와 격리된 rootless 네트워크로 전환했다. 기존 호스트 네트워크 공유를 해제했다. 코드는 이미지에 포함하며, 기존 `auth/state`만 쓰기 가능한 볼륨으로 연결한다.

이후 사용자 승인으로 이미지를 `localhost/kiki-build-auth:managed-20261025`로 교체했다. 현재 모드와 최종 외부 연결 결과는 [관리형 프록시 웹 기록](kiki-managed-proxy-web-20261025.ko.md)을 따른다. 이 문서의 엄격한 프록시 IP 검사 설명은 초기 프로필의 기록이다. 포트 매핑은 유지된다.

| 서버 주소 | 컨테이너 포트 | 용도 |
| --- | --- | --- |
| `127.0.0.1:8092` | `8092/tcp` | 기존 SSH 터널용 로그인 |
| `10.250.254.229:8092` | `8093/tcp` | Terminal Lab HTTPS 프록시 |

`podman ps`와 `podman port kiki-build-auth`에서 매핑을 확인할 수 있다. 외부 프록시는 계속 VM의 8092를 사용한다. 서버에 전체 인터페이스를 대상으로 한 새 수신 포트는 추가하지 않았다.

## 네트워크와 권한

네트워크는 `slirp4netns:cidr=10.0.2.0/24,allow_host_loopback=true,port_handler=slirp4netns`다. 이 포트 처리기는 원래 요청 출발지 IP를 보존하므로 프록시 IP 검사를 유지할 수 있다. 컨테이너의 고정 수신 주소는 `10.0.2.100`, 호스트 루프백 접근용 게이트웨이는 `10.0.2.2`다. Podman의 [네트워크 옵션 문서](https://docs.podman.io/en/v5.8.0/markdown/podman-pod-create.1.html)에 설명된 방식이다.

`--slirp-network`를 지정했을 때만 인증 프로그램이 이 고정 주소와 게이트웨이를 허용한다. 일반 실행은 기존 루프백 제한을 유지한다. 빌드 API는 `10.0.2.2:8091`, 버전·ISO API는 `10.0.2.2:8094`를 통해 접근하며, 각 작업자의 호스트 수신 주소는 루프백으로 유지된다. 전달하는 Host와 Origin도 기존 작업자가 허용하는 고정 값으로 정규화한다.

읽기 전용 루트 파일 시스템, capability 전체 제거, no-new-privileges, 메모리 256MiB, PID 128 제한을 유지한다. 외부 수신기는 출발지 `10.0.161.214`, 정확한 도메인, HTTPS 전달 헤더, Secure 쿠키 및 CSRF 검사를 유지한다. 컨테이너 이미지에 비밀번호·세션 DB는 포함하지 않았다.

## 검증 결과

- 인증 테스트 29개와 버전 관리 테스트 21개 통과. 초기 통합 테스트의 누락 모듈과 Python 패키지는 검증 환경을 실제 작업자 런타임에 맞춰 해결했다. 실패 로그도 보존한다.
- 임시 컨테이너에서 테스트 계정 로그인, 패키지 작업 API, 버전 API 모두 성공. 테스트 상태는 운영 인증 DB와 분리했다.
- 출발지 IP가 보존되는 경로에서 HTTPS 로그인 200·Secure 쿠키와 HTTP 308을 확인했다. 임시 컨테이너는 검증 후 제거하고 18092 수신을 종료했다.
- 운영 전환 직전·직후 계정과 세션 데이터 지문이 동일했다. 관리자 비밀번호는 조회하거나 재설정하지 않았다.
- 운영 루프백 로그인 200, 미인증 API 401, 비신뢰 출발지의 HTTPS 헤더 위장 403을 확인했다.
- 기존 패키지 빌드 컨테이너 ID와 버전 작업자 PID가 동일하다. 기존 인증 코드 파일도 보존했다.
- 외부 HTTPS TLS 연결은 성공하지만 HTTP 응답은 여전히 시간 초과다. 웹 프록시의 실제 출발지와 VM 연결 경로 확인이 남아 있다. 포트 매핑 전환을 외부 접속 복구 완료로 판단하지 않는다.

후속 진단에서 응답을 충분히 기다린 결과 HTTP·HTTPS 모두 `503 Service Unavailable / No server is available to handle this request.`를 반환했다. 같은 시간대에 모든 인터페이스에서 35초간 8092 패킷 메타데이터를 수집했다. 내부 시험 요청의 루프백 패킷 11개는 관찰됐지만 외부 인터페이스의 8092 패킷은 없었다. 클라우드 화면의 도메인 대상은 `10.250.254.229:8092`이며, 8092 규칙은 이 시점에 `0.0.0.0/0`로 표시됐다. 이 진단에서는 보안그룹을 수정하지 않았다. 프록시의 frontend/backend 연결, 실제 backend 주소·포트, DOWN 판정 이유와 네트워크 경로 확인이 필요하다. HTTP 상태 점검이 필요한 Host·HTTPS 전달 정보를 보내지 않아 거절되는 경우도 확인 대상이며, 아직 원인으로 확정하지 않았다.

## 재현과 복구

이미지 정의는 `deploy/container/auth.Containerfile`, 서비스 예시는 `deploy/systemd/kiki-build-auth.user.service`다. 서버에서는 원래 서비스 파일을 보존하고 `kiki-build-auth.service.d/https-ingress.conf`만 교체했다. 원래 설치기·패키지·ISO와 서버 저장소 작업본은 변경하지 않았다.

서버 기록은 `/build-kikios/kiki-build/candidates/mesa-native-20261023/auth-container-20261025`에 있다. `before`에는 이전 설정·인증 코드와 접근 제한된 SQLite 백업을 보관한다. 설정 복구 시 이전 drop-in을 되돌리고 daemon-reload 후 인증 서비스만 재시작한다. 현재 인증 DB는 그대로 사용한다. DB 백업 복원은 이후 생긴 계정·세션 상태를 잃을 수 있으므로 단순 설정 복구에 사용하지 않는다.
