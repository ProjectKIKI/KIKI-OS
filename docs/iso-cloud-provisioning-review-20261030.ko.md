# ISO 빌드 후 터미널랩·OpenStack 자동 VM 생성 검토

검토일: 2026-10-30. 소스와 공식 문서를 확인한 설계 검토이며, 이번 검토에서 클라우드 이미지 업로드·VM 생성·서비스 변경은 실행하지 않았다. 터미널랩은 로컬 체크아웃을 읽었으며 운영 배포본과 동일한지는 확인하지 않았다.

후속 구현: 같은 날 터미널랩 저장소에 ISO 업로드·SHA 검증, ISO CD-ROM과 설치 볼륨 생성, 설치 후 디스크 부팅 전환 API와 화면을 추가했다. 사용 방법은 터미널랩의 `docs/iso-vm-installation.md`에 정리했다. 소스·빌드·격리된 브라우저 동작은 확인했으며 운영 배포, 실제 OpenStack 설치, KIKI 빌드 완료 자동 호출과 외부 설치 계획 주입은 아직 수행하지 않았다. 아래 표는 최초 검토 시점의 상태다.

## 결론

구성 가능하다. ISO 빌드 성공을 별도 배포 작업의 입력으로 삼아, 시험 VM 생성과 무인 설치, 설치 디스크 부팅, 검증까지 연결하는 방식이 적합하다. VM이 `ACTIVE`가 된 상태와 OS 설치·검증이 완료된 상태를 구분해야 한다.

OpenStack 연동을 공통 기반으로 먼저 만들고, 터미널랩에는 배포 작업 등록·소유자·콘솔·결과 표시를 연결하는 구성을 권장한다. ISO 설치 검증은 계속 수행하고, 반복적인 사용자 VM 생성에는 검증한 설치 볼륨의 이미지 또는 스냅샷을 재사용할 수 있다.

## 확인한 현재 구성

| 대상 | 확인 내용 | 추가 작업 |
|---|---|---|
| KIKI ISO 작업 | `tools/ki2release.py`에서 패키지 파일·저장소 서명 확인, ISO 생성, BIOS/UEFI 카탈로그·내장 패키지 목록·ISO SHA 기록 | 완료 이벤트와 별도 VM 배포 대기열 연결 |
| KIKI 설치기 | `tools/ki2bootiso.py`에 `kiki.autoinstall`, `kiki.target`, `kiki.profile` 등 무인 설치 진입점 존재 | 외부 설치 계획과 계정·키를 읽는 경로, 완료 보고, 자동 종료 연결 |
| 무인 계정 | 현재 무인 설치 경로는 시험용 고정 `kiki` 계정/암호 사용 | VM별 계정 설정과 SSH 공개키 주입. 비밀값을 ISO·커널 명령행·빌드 로그에 기록하지 않기 |
| 설치 대상 | 대상 미지정 시 자동 디스크 선택 경로 존재 | 새로 생성한 설치 볼륨의 ID·시리얼·용량을 대조하고 명시적으로 선택. 설치 미디어·config drive 제외 |
| 펌웨어 | 현재 설치 경로는 UEFI 기반, 검증 ISO는 Secure Boot 미서명 | 처음에는 UEFI·Secure Boot 비활성 구성으로 시험 |
| KVM 장치 | 현재 커널 설정에 VirtIO 블록·SCSI·네트워크·콘솔·GPU, ISO9660·EFI 파티션 지원 선언 | 실제 대상 OpenStack에서 디스크·NIC·화면 동작 검증 |
| 기존 검증 | Hyper-V의 새 디스크 설치·두 차례 부팅·패키지 해시·nmcli·NTP·방화벽·OpenSCAP 결과가 있음 | 검사 로직을 재사용하되 VM 생성·접속 부분을 공급자별로 분리 |
| 터미널랩 | `E:/dev/terminal-lab.kr/server/heat.js`의 `createOpenstackServerDirect`는 기존 이미지 부팅 또는 이미지 기반 부팅 볼륨 생성 지원 | ISO CD-ROM과 별도 빈 설치 볼륨의 동시 생성, 이미지 업로드, 설치 후 전환 경로 추가 |
| 터미널랩 계정 주입 | 같은 함수는 계정 정보를 cloud-config user-data로 전달 | KIKI가 실제로 이 데이터를 읽도록 cloud-init 또는 KIKI 전용 초기화 도구 구현 |

KIKI 소스 검색에서는 OpenStack config drive나 metadata를 읽는 cloud-init 연동을 확인하지 못했다. 따라서 OpenStack의 keypair/user-data를 지정하는 것만으로 KIKI 계정과 SSH 키가 설정된다고 가정할 수 없다. Nova는 [config drive와 metadata](https://docs.openstack.org/nova/latest/user/metadata.html)를 제공하며, 이를 처리하는 게스트 기능이 필요하다.

## 권장 처리 흐름

```text
ISO 빌드 완료
  → ISO SHA·서명된 패키지 입력 고정
  → 배포 작업 등록
  → 프로젝트 전용 ISO 이미지 업로드
  → ISO 설치 VM + 빈 대상 볼륨 생성
  → 설치 계획 주입 및 무인 설치
  → 설치 완료 확인·정상 종료
  → 설치 볼륨으로 실행 VM 생성
  → 두 차례 디스크 부팅 및 기존 검사 실행
  → 빌드 화면에 VM·콘솔·검사 보고서 연결
```

ISO 작업의 성공 상태를 먼저 저장한 뒤 배포 작업을 등록한다. 빌드 작업자에서 장시간 VM 설치를 직접 기다리는 대신, 별도 작업자가 상태를 관리한다. 중복 방지 키는 `(ISO SHA, 공급자, 프로젝트, 설치 구성 해시)`로 잡고 생성한 이미지·서버·볼륨 ID를 저장한다. 재시도 시 같은 자원을 재사용하거나 해당 작업이 만든 자원만 정리한다.

권장 상태는 `대기 → 업로드 → VM 생성 → 설치 → 디스크 부팅 → 검증 → 준비 완료 / 실패`다. ISO 빌드 성공과 VM 설치 실패를 각각 표시한다. 용량·동시 실행 제한과 보존 기간을 두고, 실패 로그와 시험 자원은 진단할 수 있도록 남긴다.

## OpenStack의 설치 후 부팅 전환

공식 [ISO 설치 절차](https://docs.openstack.org/openstack-ansible-os_nova/latest/operational-tips/install-from-iso.html)는 ISO를 Glance에 등록하고 CD-ROM을 부팅 순서 0, 빈 설치 볼륨을 순서 1로 연결한다. 같은 문서의 볼륨 기반 CD-ROM 구성에서는 ISO가 루트 장치여서 분리할 수 없으므로, 설치된 볼륨의 스냅샷으로 새 인스턴스를 생성하는 절차를 안내한다.

따라서 최초 구현은 다음 두 단계로 잡는 것이 명확하다.

1. **설치 VM:** ISO로 부팅해 새 대상 볼륨에 KIKI 설치. 대상 볼륨은 VM 삭제 후 보존하도록 구성한다.
2. **실행 VM:** 정상 종료 후 대상 볼륨 또는 스냅샷을 부팅 장치로 사용. 디스크만으로 부팅했는지 검사한다.

운영 OpenStack의 Nova·Cinder 버전과 정책, ISO 이미지 형식 허용 여부, UEFI 펌웨어, 볼륨 부팅 가능 상태는 구현 시 확인해야 한다. 장치 버스와 펌웨어 지정은 [Glance 이미지 속성](https://docs.openstack.org/glance/latest/admin/useful-image-properties.html)을 따른다. 터미널랩의 일반 이미지 부팅 API를 그대로 호출하는 것만으로 이 설치 흐름이 완성되지는 않는다.

## 설치 계획과 첫 부팅

무인 설치용 부팅 항목과 config drive를 연결하는 방법을 권장한다. config drive에는 프로필·그룹·호스트명·대상 볼륨 식별자·SSH 공개키·저장소와 검증 키를 전달한다. 비밀번호 로그인이 필요하면 고정 시험 암호 대신 VM별 초기화 절차를 사용한다. 기존 대화형 ISO의 기본 부팅을 곧바로 디스크 초기화 모드로 바꾸지 않는다.

외부에서 설치 계획을 받아 현재 InstallPlan 계약으로 검증·실행하는 어댑터가 필요하다. 설치가 끝나면 작업 ID와 일치하는 완료 보고를 남기고 정상 종료해야 한다. 현재의 콘솔 문구 출력과 설치 메뉴 복귀만으로 완료 여부를 판단하지 않는다.

복제용 이미지를 만들 경우에는 정상 종료한 설치 볼륨을 이미지화하고, 복제 VM마다 machine-id·SSH 호스트 키·네트워크 초기화가 독립적으로 수행되도록 준비한다. 이 경로도 먼저 실제 ISO 설치에서 나온 결과임을 기록한다.

## 터미널랩 연동 범위

- KIKI 빌드 화면: 공급자, 프로젝트, Flavor, 네트워크, 설치 볼륨 크기, 설치 프로필 선택과 자동 생성 여부 저장.
- 공통 작업자: OpenStack 이미지·볼륨·VM 생성, 상태 확인, 완료 보고 검증, 오류 수집 담당.
- 터미널랩: 기존 소유자 관리·프로젝트 제한·Quota 차단·VNC/SSH 연결 흐름을 유지하면서 ISO 배포 작업을 등록하는 인증 API 추가.
- 인증: 사람의 웹 로그인 세션 대신 자동화용 서비스 인증 사용. 직접 OpenStack 연동에는 프로젝트와 권한을 제한한 [Application Credential](https://docs.openstack.org/keystone/latest/user/application_credentials.html) 사용을 검토.

별도 터미널랩 전용 인증 API가 준비되기 전에는 OpenStack 작업자를 먼저 구현할 수 있다. 이 경우 터미널랩 화면에 VM을 관리 대상으로 등록하는 절차를 별도로 연결해야 한다. 직접 Nova로 생성한 VM이 자동으로 터미널랩 사용자 소유 자원 목록에 나타난다고 가정하지 않는다.

## 완료 판정과 권장 구현 순서

처음에는 기존 Hyper-V 시험과 같은 2 vCPU·RAM 4GB·디스크 32GB를 시작점으로 삼고, 해당 프로젝트의 Flavor와 Quota에 맞춘다. 구현 순서는 다음과 같다.

1. OpenStack 시험 프로젝트에서 ISO 업로드, UEFI 부팅, VirtIO 장치, 설치 볼륨 보존·디스크 부팅을 수동으로 확인.
2. 설치 계획·계정·키 주입과 완료 보고를 추가하고, 새 볼륨에서 무인 설치 검증.
3. ISO 완료 이벤트와 OpenStack 배포 작업자를 연결. 중복 실행·실패 복구 시험.
4. 터미널랩 인증 API와 소유자·콘솔·결과 화면 연결.
5. 검증된 설치 볼륨의 이미지화를 추가해 반복 VM 생성에 활용.

완료 기준은 API의 VM 생성 성공뿐 아니라 실제 설치 패키지·파일 해시, ISO 없는 두 차례 부팅, DHCP/DNS/HTTPS, SSH, 기본 KI2 저장소 서명 검증, nmcli, 시간 동기화, 실제 방화벽 패킷 차단, 기존 OpenSCAP 설정 9개 통과다. GNOME 서비스·로그인 화면과 실제 사용자 GUI 로그인 검증도 구분해서 표시한다. 안정 채널 승격은 이 자동 시험과 분리한다.

이 문서는 최초 검토 시점의 제안이다. 이후 적용한 운영 API·무인 설치·검증 경로와 실제 산출물은 [ISO 자동 배포 운영 기록](iso-cloud-automation-20261030.ko.md)에 정리한다.
