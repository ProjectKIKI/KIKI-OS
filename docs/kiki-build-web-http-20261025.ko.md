# 빌드 웹의 일반 HTTP 구성

최신 운영 결과는 [외부 빌드 웹 로그인 복구](kiki-build-web-port80-restored-20261025.ko.md)를 참고한다. 승인한 80 → 8092 OS 포트 매핑과 허용 HTTPS 주소 갱신으로 외부 로그인 화면을 복구했다. 아래 내용은 기존 HTTP 인증 컨테이너의 구성 기록이다.

빌드 웹에서 외부 프록시 전용 기능을 제거하고 하나의 HTTP 수신기와 로그인 기능으로 정리했다. 터미널랩 서비스가 외부 연결을 담당한다. 웹 앱에는 프록시 출발지 목록, 전달 헤더 해석, 프록시 모드, 별도 프록시 수신기가 없다.

## 실행 구성

- 이미지: `localhost/kiki-build-auth:http-r2-20261025`.
- 컨테이너 수신: `10.0.2.100:8092` 한 개.
- 호스트 매핑: `127.0.0.1:8092 → 8092`, `10.250.254.229:8092 → 8092`.
- 활성 systemd drop-in: `kiki-build-auth.service.d/web-http.conf`.
- 이전 `https-ingress.conf`는 백업한 뒤 활성 설정에서 제거했다.
- 원래 인증 DB는 동일한 `auth/state` 볼륨으로 유지한다. 코드만 전용 이미지에 포함한다.

기존 패키지 작업자와 버전·ISO 작업자는 그대로 사용한다. 웹의 작업 요청은 고정된 내부 API로 전달한다. 기존 설치기·원본 패키지·ISO·서버 저장소 작업본을 이관하거나 수정하지 않는다.

## 로그인과 상태 점검

`--origin`은 일반 웹 앱의 허용 접속 주소 설정이다. 공개 HTTPS 도메인에서는 Secure 쿠키를 사용하고, 기존 SSH 터널의 루프백 HTTP 주소에서도 로그인할 수 있다. 같은 Host에 HTTP와 HTTPS를 동시에 지정하는 모호한 설정은 거절한다. 쿠키 보안 정책은 등록된 Host의 주소로 결정하며 `X-Forwarded-*` 헤더를 읽지 않는다.

공개 접속의 로그인·API는 정확한 Host, HTTPS Origin, 세션·CSRF·시도 횟수 제한을 유지한다. 로그인 링크는 `/login` 상대 경로를 사용하므로 SSH 터널에서도 현재 접속 주소를 유지한다. 데이터가 없는 루트 안내 페이지와 `/healthz`는 익명 상태 점검에 응답하며, 빌드·로그·버전·ISO·다운로드에는 인증이 필요하다.

인증 테스트 28개가 통과했다. 테스트 계정의 공개 주소·루프백 주소별 로그인과 패키지·버전 API 호출도 확인했다. 임시 검증 컨테이너에는 운영 인증 DB를 연결하지 않았고 검증 후 제거했다. 운영 교체 직전·직후 계정·세션 지문과 기존 빌드 컨테이너 ID·버전 작업자 PID가 같았다. 운영 루트 안내 페이지와 로그인은 200, 미인증 API는 401이다. 전달 헤더의 값이 달라도 공개 주소의 Secure 쿠키 정책과 루프백 HTTP 로그인 정책이 유지되는지 확인했다.

## 기록과 복구

서버 후보와 기록은 `/build-kikios/kiki-build/candidates/mesa-native-20261023/auth-http-20261025`와 그 하위 `r2`에 보관한다. 이전 설정·이미지·접근 제한된 SQLite 백업을 유지한다. 설정 복구 시 이전 drop-in과 이미지로 인증 서비스만 재시작하며, 현재 인증 DB는 유지한다.

앞선 관리형 프록시 모드는 이전 구성 기록이다. 일반 HTTP 서비스로 정리한 뒤에도 공개 HTTPS 도메인은 503을 반환했다. 현재 웹 서비스와 외부 도메인의 응답 결과는 이번 배포 보고서를 기준으로 판단한다. 서버 HTTP 응답 성공을 외부 도메인 복구 성공으로 표시하지 않는다.
