# KI2 유지보수 업데이트

업데이트 관리 화면은 `/updates`이다. 원본 버전 확인, 후보 빌드, 설치된 VM 검증, 안정 채널 승격을 각각 기록한다. 발견한 버전을 자동으로 레시피에 반영하거나 안정 채널에 배포하지 않는다.

## 운영 흐름

1. 원본 버전 확인 결과에서 변경 패키지를 선택하거나 직접 후보를 준비한다. 같은 원본 버전이면 KI2 `release`가 증가한다. 새 버전은 새 HTTPS 소스 주소를 입력한다.
2. 기준 스냅샷, 소스 SHA-256, 레시피, 함께 재빌드할 패키지와 호환성 판단을 검토한다. 임시 staging 경로를 복사하는 레시피는 실제 소스 빌드 방식을 복구하기 전까지 제출할 수 없다.
3. 후보 빌드는 기존 CI 대기열을 사용한다. 기준 바이너리의 해시를 검사해 의존 입력으로 쓰고, 변경 대상만 빌드한다. 재시도는 보관한 계획과 소스 입력을 사용한다.
4. 후보가 완성되면 전용 VM 검증을 요청한다. 로컬 검증기가 요청의 nonce와 계획·기준·후보 해시를 확인하고, 설치된 패키지가 기준의 부분집합이며 모든 변경 대상이 포함됐는지 검사한다.
5. 서명된 검증 보고서가 도착하면 결과 확인 버튼으로 검증한다. 모든 필수 검사가 통과한 후보에만 수동 안정 채널 승격 버튼이 나타난다. 후보 작성 이후 안정 채널이 바뀌면 승격을 거부한다.

알림은 빌드 콘솔 안에 표시한다. 기본 확인 주기는 6시간이다. GNOME cache.json, GitHub Releases, 일부 공식 배포 디렉터리를 사용하며, 미지원 공급자는 직접 확인, 통신 실패는 확인 실패로 표시한다. GNOME 40 이전 라이브러리와 Linux는 설치된 major.minor 계열만 추적한다. 다른 major 또는 유지보수 계열로 이동하려면 직접 검토한다. 원본 배포처 검색은 원저자 서명 검증을 대신하지 않는다.

## 서버 구성

기존 release worker 저장소의 `updates/` 아래에 설정, 확인 결과, 후보, 고정 빌드 계획, 검증 보고서와 안정 채널 이력을 보관한다. `deploy/updates/recipes.json`은 기존 데스크톱 바이너리와 레시피 지문을 대조한 입력이다. 갱신된 바이너리의 다음 업데이트는 이전 고정 계획의 레시피를 사용한다.

CI 컨테이너에는 계획, 바이너리·소스 객체, 스냅샷과 승인된 빌드 소스를 읽기 전용으로 마운트한다. 저장소의 개인 서명 키는 CI에 마운트하지 않는다. 공유 입력 볼륨은 Podman의 소문자 `z` 레이블을 사용한다. 한 컨테이너 전용 `Z` 레이블로 바뀌면 다른 작업자가 새 입력을 읽지 못한다. 새 파일을 코드 마운트에 추가한 뒤에는 컨테이너를 재생성해 기존 Podman SELinux 레이블을 적용한다. 컴파일러 자체는 기존 호스트 컨테이너 툴체인을 사용한다.

`updates-testing` 채널은 완료된 후보를 공개한다. `stable` 채널은 `updates/stable.json`의 `version`에 지정한 스냅샷만 신규 게시한다. 버전별 URL은 `/ki2/versions/<channel>/<snapshot>/`이고, 채널별 인덱스는 `/ki2/<channel>/repo/index.x86_64.json`이다. 기존 버전과 패키지는 진행 중인 다운로드를 위해 보존한다. 원본 출처 목록은 각 경로의 `sources.html`이다.

현재 서명은 시험 저장소 키이다. 공식 릴리즈·Secure Boot 인증을 의미하지 않는다. 공개 저장소는 허용 목록에 있는 파일만 제공하며 검증 키·보고서용 개인 키·서버 설정은 게시하지 않는다.

## 설치된 시스템에 적용

서명 키 지문을 별도로 확인하고 고정된 버전 URL을 사용한다.

```sh
sudo ki2ctl --repo https://YOUR-HOST/ki2/versions/stable/APPROVED-SNAPSHOT \
  offline-stage --verify-key /etc/ki2/keys/APPROVED-PUBLIC-KEY PACKAGE...
sudo systemctl reboot
```

`offline-stage`는 서명·인덱스·패키지와 실행 도구를 고정하고 `/system-update`를 만든다. 다음 부팅의 `system-update.target`에서 적용한 뒤 정상 부팅으로 돌아간다. 코어 패키지의 실행 중 교체는 차단한다. 사용자 수정 `/etc` 파일을 보존하고 새 기본값은 `.ki2new-<transaction>` 파일로 남긴다. 성공 기록과 실패 입력은 `/var/lib/ki2/offline-*`에 보관한다.

파일 교체는 심볼릭 링크의 마지막 경로 요소를 따라가지 않는다. 일반 파일은 같은 디렉터리의 임시 파일에 쓰고 교체해 실행 중인 프로세스가 참조하는 기존 라이브러리 inode를 보존한다. 예상 밖 예외도 오프라인 부팅 표시를 제거하도록 처리한다. 새 base-files에는 설치된 CA 묶음을 OpenSSL 기본 경로에 연결하는 tmpfiles 설정이 포함된다.

커널 복구 도구는 루트 디스크의 GPT 헤더·파티션 배열 체크섬을 검증해 ESP를 찾는다. 최소 OS에 없는 `lsblk`를 요구하지 않는다. ESP의 현재 커널·initramfs 해시를 보관하고 `kiki-recovery` GRUB 항목을 추가한다. Linux 갱신 시 기본 부팅 파일도 ESP에 반영한다. 이전 커널 부팅 기능이며 전체 루트 파일시스템 롤백은 아니다. 전체 복구는 VM 검사 전 체크포인트 또는 별도 백업을 사용한다.

현재 `kernel` 레시피는 새 initramfs를 생성하지 않으므로 이 화면의 커널 후보 제출은 차단한다. 새 커널은 기존 커널·ISO 빌드 경로로 검증한다. 유지보수 패키지 갱신 후 기존 커널 복구 부팅과, 새 커널 버전으로의 갱신 검증은 별개다.

## 로컬 Hyper-V 검증기

`tools/ki2updatevm.py`와 `tools/ki2updatevm.ps1`은 등록한 전용 시험 VM만 다룬다. 현재 시험 대상은 `kiki-gnome-apps-r3-20261028`이며, 이름·UUID·디스크 경로를 모두 대조한다. 전원을 끈 뒤 디스크 체크포인트를 만들고 갱신한다. 체크포인트를 자동 삭제하지 않는다.

구성 JSON에는 서버 SSH 키 경로와 known-hosts, 게스트 접속 설정, VM UUID, 저장소 공개 키 지문, 검증 서명 키 경로를 지정한다. 개인 키와 구성 JSON은 Git에서 제외하고 Windows 사용자 ACL로 제한한다. 서버에는 검증 공개 키만 전달한다.

```powershell
python tools/ki2updatevm.py --config artifacts/update-validation-20261028/config.json
# 수동 검증이 완료된 뒤 요청 감시 등록
./tools/register_ki2update_validator.ps1 -ConfigPath artifacts/update-validation-20261028/config.json
```

검증은 패키지 해시, 실제 `/etc/profile` 변경 보존, 서비스, 재부팅, 복구 커널과 기본 커널 재부팅, GNOME Wayland 로그인 화면을 확인한다. 사용자 로그인과 앱 조작은 별도 수동 확인 대상이다. 보고서 서명은 후보·nonce·VM·구성·필수 검사에 연결된다. 로컬 검증기는 안정 채널을 승격하지 않는다.

예약 작업은 사용자 로그인 중에만 실행한다. Hyper-V 관리 권한이 필요하며 2분마다 명시적으로 요청한 후보만 확인한다. VM이 이미 다른 후보로 갱신됐다면 기준 구성 검사에서 중단한다. 다음 후보 검사 전 적절한 기준 체크포인트로 복구하거나 새 시험 VM을 준비해야 한다.
