# KIKI Server Shell: GNOME 픽셀 데스크톱과 경량 세션 실행 계획

- 작성일: 2026-11-05 (Asia/Seoul)
- 확인 기준: 저장소 커밋 `876554ab8258`와 작성 시점의 작업 트리.
- 목적: **1. GNOME판 완성 → 2. 운영 기능 분리 → 3. 경량 세션 시제품 → 4. 측정 후 채택** 순서로 진행한다.
- 현재 상태: 1단계 픽셀 디자인·운영 확장·전용 세션과 r6 서명 후보를 구현했다.
  Hyper-V에서 로그인·테마·Polkit 복구·재부팅·일반 GNOME 복귀와 원본 보존을 확인했다.
  배경 잘림·관리자 최소화 복귀·셸 내부 대비와 스타일은 독립 후보에서 보완했다.
  관리자 완료 창·브라우저·기존 런타임 경고와 실제 한글 조합 입력 검증이 남아 있어 공개 운영 후보로 승격하지 않았다.
  최신 범위와 증거는 [r6 UI/UX 검증 기록](kiki-paper-pixel-ui-r6.ko.md), 이전 이력은 [1단계 후보 기록](kiki-paper-pixel-stage1.ko.md)을 따른다.
  2~4단계 완료나 경량 세션·성능 비교 완료를 뜻하지 않는다.

## 1. 제품 방향과 경계

첫 제품은 **KIKI Server Desktop — GNOME Edition**으로 구성한다.
기존 GDM/Wayland·GNOME Shell·Mutter, GNOME 설정·Nautilus·Console을 재사용하고,
KIKI 관리자와 픽셀 스타일, 작은 운영 상태 확장을 추가한다.

이후 **KIKI Server Shell — Lite Lab**을 별도 실험 세션으로 구성한다.
GNOME판에서 검증한 관리자·CLI·권한 처리·디자인 자산을 재사용하되,
세션과 compositor의 구성은 독립적으로 평가한다. Lite Lab은 4단계 채택 판정 전까지
운영 기본값이나 설치기의 기본 선택이 아니다.

| 항목 | 방침 |
| --- | --- |
| GNOME Base | 1차에는 GNOME 세션 전체를 재사용. 경량판에는 GTK·GLib·앱·관리 기능을 공통 기반으로 사용 |
| 시각 디자인 | KIKI Paper Pixel: 픽셀 아이콘, 각진 패널, 선명한 테두리, 얕은 단색 그림자 |
| 운영 기능 | 별도 KIKI 관리자·CLI·backend·제한된 권한 helper에 배치 |
| GNOME 셸 확장 | 상태 표시와 앱 실행. 조회·분석·패키지 작업의 본체를 넣지 않음 |
| AI | incident-ai 웹 연결. 로컬 상주 LLM이나 셸 내 AI 엔진은 이 범위에 포함하지 않음 |
| 구현 언어 | 기존 관리자 C/GTK4·Libadwaita와 Python backend를 재사용. GNOME 확장은 GJS. Rust 이관은 별도 필요성 검토 |
| 장기 경량화 | GNOME 포크나 자체 compositor 개발보다 기존 경량 compositor 재사용을 우선 검토 |
| 서버 기본 설치 | 기존 headless 서버 구성을 유지하고 데스크톱은 선택형으로 제공 |

픽셀 디자인 적용과 메모리·CPU 감소는 서로 다른 목표다. 디자인 변경만으로
Xfce 수준의 사용량이나 성능 향상을 달성했다고 표시하지 않는다.

## 4. 1단계 — GNOME판 완성

### 작업 순서

- [ ] **P1-01 기준선 고정**: 커밋·dirty 변경 목록, SDK·컴파일러·GNOME/Mutter/GTK 버전,
  후보 인덱스·공개키·패키지·기존 ISO SHA를 기록한다. 원본을 건드리지 않는 전용 VM에서
  기존 GNOME 로그인·로그아웃·재부팅·기본 앱·한글 입력·관리자 동작과 초기 성능을 수집한다.
- [ ] **P1-02 후보 빌드 준비**: `build_kiki_admin.py`의 고정 baseline·서명 ID·채널과
  현재 r4 프로필의 차이를 정리한다. 기존 명세 검증을 유지하면서 명시한 새 후보를
  처리하도록 보완한 뒤 사용한다. r4를 그대로 인수에 넣어 동작한다고 가정하지 않는다.
- [ ] **P1-03 디자인 토큰·자산**: 라이트·다크, 정상·주의·실패·선택·포커스,
  간격·테두리·그림자 규칙과 픽셀 아이콘을 고정한다. 미리보기 이미지를 실제 화면과 비교한다.
- [ ] **P1-04 관리자 앱 적용**: 앱 범위의 스타일과 자산을 적용한다.
  기존 조회·검토·인증·결과 흐름과 GTK 키보드 탐색·접근성 의미를 유지한다.
- [ ] **P1-05 GNOME 운영 확장**: 상단에 로컬 호스트·실패 서비스 수와 관리자·로그·터미널·
  incident-ai 진입점을 제공한다. 지원 GNOME 버전을 명시하고 내부 메서드 대체는 최소화한다.
- [ ] **P1-06 운영 세션 후보**: GDM에 별도 운영 세션을 등록하고 사용자 systemd 서비스의
  시작·종료를 연결한다. 확장·자동 실행이 일반 GNOME 세션으로 새지 않는지 검증한다.
- [ ] **P1-07 서명·VM 검증**: 별도 후보를 패키징하고 파일 소유권·SHA·의존성·서명과
  실제 GDM/Wayland 로그인·로그아웃·재로그인·재부팅을 검증한다.

### UI/UX 기준

| 영역 | 구성 |
| --- | --- |
| 상단 패널 | 현재 로컬 장비, 실패 서비스 수, 네트워크 상태, 시각. 오류·오래된 값은 별도 표시 |
| 앱 실행 | 관리자, GNOME Console, Nautilus, 로그, 시스템 감시, incident-ai. 실제 공급한 앱만 노출 |
| 관리자 | 현재 장비·실패 서비스 → 관련 로그·터미널 → 조치 검토 → 인증 → 결과 확인 |
| 스타일 | 1~2px 테두리와 2~4px 단색 그림자를 기본 배율의 시안 기준으로 사용 |
| 글꼴 | 로고·짧은 장식에만 픽셀 느낌. 한글 본문·오류 메시지는 일반 글꼴, 로그는 고정폭 |
| 배율 | 100%·125%·150%와 큰 글자·고대비를 확인. 픽셀 정렬을 위해 사용자 배율을 제한하지 않음 |
| 상태 표시 | 색상에 아이콘·텍스트를 함께 사용. 깜박이는 경고·계속 움직이는 장식은 제외 |
| 창 동작 | 이동·크기 변경·최대화·포커스·작업 전환 유지. 업무 창을 강제로 재배치하지 않음 |

GNOME 확장은 GJS/St로 작성한다. GNOME Wayland에서 GTK4 Layer Shell 패널이
동작한다고 가정하지 않는다. 일반 GNOME 앱 전체에 전역 CSS를 강제 주입하지 않고,
공유 색상·아이콘과 KIKI 앱 자체의 스타일을 중심으로 일관성을 맞춘다.

GSettings·확장 활성화는 같은 사용자에서 세션 간 공유될 수 있다. 시험용 사용자와
해당 세션의 활성화 조건을 구분하며, 단순히 GDM 메뉴를 추가한 것을 설정 격리로 취급하지 않는다.

### 완료 조건

- 일반 GNOME으로 돌아가도 로그인과 기본 앱이 정상이고 원래 설정으로 복구할 수 있다.
- 서비스 실패 탐지·로그·터미널·검토·사용자 인증·재시작·결과 확인을 실제 전용 서비스로 검증한다.
- 셸 확장을 꺼도 관리 앱·CLI가 동작하고, 확장 예외가 반복 재시작을 유발하지 않는다.
- 라이트·다크와 작은 화면에서 버튼·경고·로그가 잘리지 않고 키보드로 조작할 수 있다.
- UI 캡처, 테스트 결과, 패키지 해시와 실제 로그인·인증 증거가 같은 후보 식별자에 연결된다.

## 5. 2단계 — 운영 기능을 셸과 분리

### 공통 구조

```text
GNOME 운영 확장 / 향후 Lite 패널
          │ 상태 표시·앱 실행
          ▼
KIKI 관리자 ── 공통 CLI / JSON backend ── 시스템 조회
                         │ 계획 검토
                         ▼
                  Polkit + 제한된 helper
                         │ 승인된 작업 실행
                         ▼
                  결과 재조회·오류 표시

incident-ai 웹: 별도 분석 서비스, 명시적으로 선택한 문맥만 전달
```

### 작업 순서

- [ ] **P2-01 계약 문서화**: 기존 `kiki-admin-v1`의 필드·시간·오류·종료 코드·스키마 버전,
  조회·계획·실행·진단 범위를 명세한다. 아직 없는 필드·명령은 구현 예정으로 구분한다.
- [ ] **P2-02 비동기 조회**: 셸에는 짧은 timeout·취소·실패 상태를 제공한다.
  실시간 로그·긴 패키지 작업·지속적인 root 실행은 셸에서 수행하지 않는다.
  새 상주 daemon은 필요성과 사용량을 검증한 경우에만 추가한다.
- [ ] **P2-03 권한 경계**: 사용자 권한 조회와 인증이 필요한 로그·변경 작업을 분리한다.
  helper의 임의 명령·셸·대상 루트 거부, 검토 후 상태 변경 거부, 기존 KI2 잠금을 유지한다.
- [ ] **P2-04 앱 실행·AI 연결**: 설치된 desktop ID와 구성된 incident-ai HTTPS 주소를 사용한다.
  incident-ai의 실제 deep-link/API 규약 확인 전에는 기본 주소 열기만 제공한다.
  서버 ID·서비스·시간 범위 전달은 규약 확인 후 추가하며 원문 로그·토큰을 URL에 넣지 않는다.
- [ ] **P2-05 셸 독립 시험**: GNOME 확장을 끈 상태와 별도 사용자 세션에서 같은 CLI·관리자
  결과를 검증한다. 원격 서버 전환은 현재 로컬 계약에 섞지 않고 별도 전송·인증 설계로 남긴다.

### 완료 조건

- 같은 backend/CLI를 두 셸 어댑터가 재사용할 수 있고, 기본 조회에 GNOME Shell 내부 API가 필요 없다.
- 정보 조회 실패·timeout·오래된 값·부분 응답이 정상 상태나 실패 서비스 0개로 표시되지 않는다.
- 인증 취소·권한 부족·로그 접근 거부·검토 이후 변경·중복 실행을 각각 검증한다.
- 전체 GUI를 root로 실행하지 않고, 실제 Polkit 다이얼로그 인증은 helper 직접 시험과 구분해 기록한다.
- 관리자 창·셸 종료가 실행 중인 패키지 작업의 잠금·결과 기록을 훼손하지 않는다.

## 6. 3단계 — 별도 경량 세션 시제품

### 1차 평가 후보

**labwc + GTK4/gtk4-layer-shell 패널 + 기존 KIKI 관리자**를 첫 평가 대상으로 삼는다.
이는 경량판 실험 후보이며 채택이나 새 의존성 버전 확정을 뜻하지 않는다.

labwc는 wlroots 기반 Wayland compositor이고 패널·배경 등의 기능은 클라이언트와
조합한다. GTK4 Layer Shell은 지원 compositor 위의 패널 구현에 사용한다.
일반 GNOME Wayland에서는 지원되지 않으므로 GNOME판 확장과 패널 구현을 나눈다.

현재 GNOME Shell을 포크하거나 Mutter를 단순 실행한 상태를 완성된 Lite 세션으로
배포하지 않는다. 잠금 화면·입력기·포털·알림은 제공 주체를 반드시 지정한다.

### 작업 순서

- [ ] **P3-01 의존성 잠금**: labwc·wlroots·gtk4-layer-shell과 포털·알림·잠금·인증 에이전트의
  공급 패키지·버전·공식 URL·SHA·서명·라이선스·빌드 순서와 KIKI ABI 호환성을 확정한다.
- [ ] **P3-02 프로토콜 검증**: Layer Shell, 잠금, 화면 출력, 작업/창 목록 제어,
  클립보드와 입력기 연동에 필요한 compositor 기능을 시험한다. GNOME의 창 제어 코드를 그대로 이식하지 않는다.
- [ ] **P3-03 최소 패널**: 시각·현재 장비·실패 서비스 수·앱 실행·로그아웃을 제공하고,
  창 전환·작업 공간과 키보드 탐색을 검증한다. 패널 종료 시 기존 앱이 유지되는지 확인한다.
- [ ] **P3-04 세션 통합**: GDM 선택 항목, 사용자 D-Bus·systemd·환경 전달,
  Polkit 에이전트·키링·GSettings·한글 입력·포털·알림·실제 잠금을 구성한다.
- [ ] **P3-05 GNOME 앱 호환성**: Nautilus·Console·KIKI 관리자와 파일 선택·문서 포털·
  외부 링크·키보드 입력을 확인한다. GNOME 설정은 기능별 지원/미지원 항목을 명시한다.
- [ ] **P3-06 장애·복구**: 패널·compositor 종료, 인증 에이전트 부재, 오프라인,
  사용자 서비스 실패를 시험하고 일반 GNOME·TTY·SSH로 복구한다.

### 실험 범위와 완료 조건

- 별도 사용자·VM·후보 패키지에 설치하고 기존 GNOME 프로필·개인 설정·패키지·ISO를 보존한다.
- 잠금·사용자 인증·한글 입력·로그아웃이 미완료이면 공개 운영 후보로 승격하지 않는다.
  자동 로그인이나 잠금 해제로 시험을 통과시키지 않는다.
- 기본 GNOME 앱이 실행된다는 사실과 모든 GNOME 설정 패널이 동작한다는 사실을 구분한다.
- GUI·패널·CLI의 권한 경계가 2단계와 같고, 각 세션 서비스의 종료가 확인된다.
- 실제 Hyper-V 디스크 부팅·GDM 로그인·재로그인·재부팅 증거를 확보한다.

## 7. 4단계 — 같은 조건에서 측정하고 채택

### 비교군과 환경

| 비교군 | 목적 |
| --- | --- |
| A. 기존 GNOME 기준 후보 | 시각 변경 전 성능·기능 기준 |
| B. KIKI GNOME Edition | 픽셀 디자인·운영 확장의 추가 비용 확인 |
| C. Lite Lab | 기능 호환성을 유지하면서 자원 감소가 있는지 확인 |

- 같은 Hyper-V 세대, 고정 2 vCPU·4 GiB RAM을 1차 기준으로 사용하고 동적 메모리는 끈다.
  이는 측정 환경 제안이며 기존 VM의 리소스를 변경하라는 명령이 아니다.
- 같은 커널·파일시스템·디스크 크기·해상도·배율·앱 버전·서비스·네트워크 조건을 기록한다.
  달라야 하는 compositor·세션 구성과 의존성 차이는 명세에 남긴다.
- 시험별 새 작업 디렉터리와 VM을 쓰고 기존 VHDX·ISO·VM을 덮어쓰지 않는다.
- GPU/DRM 장치와 renderer, 하드웨어 가속/소프트웨어 렌더링 여부를 기록한다.
  Hyper-V·물리 장비·WSL 수치를 같은 그래프에서 동등한 결과로 비교하지 않는다.
- 업데이트·인덱싱·동기화가 끝난 뒤 로그인 후 대기 시간을 고정한다.
  동일 시나리오를 최소 5회 수행하고 중앙값·최솟값·최댓값과 실패 횟수를 남긴다.

### 측정 시나리오와 증거

| 시나리오 | 지표·확인 항목 |
| --- | --- |
| 부팅·로그인 | `systemd-analyze time`, GDM 표시 시간, 인증 완료 후 패널과 입력 준비까지의 시간 |
| 유휴 세션 | 정해진 안정화 시간 후 시스템 `MemAvailable`, 세션 프로세스별 PSS, 120초 CPU 사용량·재시작 수 |
| 터미널·관리자 | 실행부터 조작 가능한 화면까지의 시간, 한글 입력, 메모리·CPU 증가량 |
| 브라우저·AI | 같은 브라우저·프로필·탭·페이지로 별도 측정. 네트워크 응답 시간과 로컬 UI 비용 분리 |
| 운영 흐름 | 전용 실패 서비스 탐지 → 로그·터미널 → AI 연결 → 검토 → 인증 → 재시작 → 상태 재확인 |
| 표시·입력 | 배율 변경·해상도 변경, 키보드 탐색, 클립보드, 파일 선택·문서 포털 |
| 장애·복구 | 패널 종료·compositor 장애·오프라인·인증 취소, 로그아웃 후 서비스 잔존 여부 |

부팅 전체 시간은 로그인 후 준비 시간의 대용값으로 사용하지 않는다. SSH의
`graphical-session.target` 활성 시각만으로 실제 사용자 조작 준비가 끝났다고 판정하지 않는다.
CPU는 1 vCPU를 100%로 하는 집계인지 전체 vCPU로 정규화한 값인지 명시한다.

PSS는 RSS 단순 합계와 구분해 `/proc/*/smaps_rollup`의 측정 가능한 프로세스로 집계한다.
권한 때문에 읽지 못한 프로세스, 수집기 자체, 별도 브라우저 프로세스의 포함 여부를 기록한다.
측정 누락을 0으로 채우거나 PSS·RSS·시스템 메모리 감소량을 서로 같은 지표로 비교하지 않는다.

### 작업 순서와 판정

- [ ] **P4-01 수집 규약**: 측정 대상 프로세스·서비스, 안정화 시간, 준비 완료 이벤트,
  스키마·timeout·누락 처리·호스트 정보의 수집 규칙을 고정한다.
- [ ] **P4-02 수집 도구**: 권한 상승 없는 수집기를 우선 만들고 필요한 시스템 지표의
  한계는 표시한다. 측정을 위해 서버·사용자 서비스나 인증 정책을 자동 변경하지 않는다.
- [ ] **P4-03 반복 측정**: A/B/C의 동일 시나리오와 기능·장애 시험을 실행한다.
  기존 특정 VM에 고정된 `ki2gnomevmreport.py`는 범용 성능 도구로 직접 재사용하지 않는다.
- [ ] **P4-04 채택 검토**: 기능 회귀·자원 차이·업스트림 추종 비용을 평가하고 결정을 기록한다.
- [ ] **P4-05 배포·복구**: 채택한 경우에만 별도 서명 릴리즈·설치 선택 항목·지원 범위를 정하고,
  일반 GNOME 복귀와 이전 릴리즈 부팅을 실제 검증한다.

**판정 순서:** 잠금·권한·한글·로그인·필수 앱·복구가 먼저 통과해야 한다.
그다음 반복 측정의 편차를 넘는 자원 감소와 유지보수 비용을 검토한다.
수치 목표는 A 기준선을 수집한 뒤 C 측정 전에 고정하고, C 결과를 본 뒤 유리하게 바꾸지 않는다.
개선이 작거나 호환성·복구가 악화되면 GNOME판을 유지하고 Lite는 실험 세션으로 남긴다.

## 8. 파일·패키지·검증 산출물 배치

아래 신규 이름은 **계획상 경로·패키지 이름**이다. 이 문서 작성으로 해당 구현이나
KI2 명세가 생성·등록되지는 않는다. 기존 경로와 충돌 여부를 확인한 뒤 단계별로 추가한다.

| 대상 | 제안 위치 | 도입 단계 |
| --- | --- | --- |
| 공통 픽셀 디자인·아이콘 | `assets/desktop/paper-pixel/` | 1 |
| GNOME 운영 확장 | `desktop/gnome/kiki-ops/` | 1 |
| GNOME 운영 세션 소스 | `distro/sources/kiki-session-gnome-ops/` | 1 |
| 앱 범위 스타일 | `cmd/kiki-admin/`의 별도 스타일·리소스 | 1 |
| 공통 backend 계약 | `docs/kiki-admin-api.ko.md` | 2 |
| 공통 CLI·권한 정책 | 기존 `distro/sources/kiki-admin/` | 2 |
| Lite 패널·세션 소스 | `desktop/lite/`, `distro/sources/kiki-session-lite-lab/` | 3 |
| 별도 후보 프로필 | `distro/profiles/desktop-gnome-ops.toml`, `desktop-server-lite-lab.toml` | 1 / 3 |
| 비교 측정 도구 | `tools/kiki_session_bench.py` | 4 |
| 작업·검증 결과 | `artifacts/server-shell/<날짜>-<커밋>-<후보>/` | 전 단계 |

자산, 확장, 세션, 관리자, compositor 의존성을 각각 패키징한다. 새 세션은 필요한
패키지가 서명 저장소에 들어 있고 의존성 폐쇄·실제 로그인이 검증된 후 설치 선택에 노출한다.
앱 설치 여부와 세션 선택 가능 여부를 별개로 관리한다.

결과 디렉터리에는 최소한 입력 커밋·작업 트리 변경, SDK/도구 지문, 원본·후보 해시,
패키지 인덱스·서명 검증, VM 구성, 기능 시험 JSON, 측정 원본·요약,
라이트·다크 캡처와 복구 결과를 연결한다. 암호·토큰·개인키·전체 인증 DB는 넣지 않는다.

## 9. 기존 환경 보존과 복구

1. 현재 설치기·패키지·ISO·프로필·서명 저장소를 기준선으로 고정하고 새 후보에만 쓰기 작업을 한다.
2. 같은 이름의 패키지가 있어도 불변 저장 객체·고정 릴리즈를 덮어쓰지 않는다.
   패키지 내용이 바뀌면 release와 레시피/소스 지문도 갱신한다.
3. 새 세션을 기본값으로 바꾸기 전에 일반 GNOME 선택과 TTY·SSH 복구를 확인한다.
4. 시험용 GSettings·확장 설정을 기록하고 새 시험 사용자로 격리한다. 복구할 때 전체 사용자
   dconf를 초기화하거나 GNOME 앱·사용자 홈을 삭제하지 않는다.
5. 기존 GNOME 앱과 라이브러리 ABI를 유지한다. 새 compositor 전용 포털·에이전트가
   일반 GNOME 세션의 공급자 선택을 가로채지 않는지 확인한다.
6. Git 전송은 기존 정책대로 HTTPS를 사용한다. 후보 실행에는 커밋·소스 SHA를 고정하고
   새 빌드·서명·ISO 생성·릴리즈 승격을 구분한다.

## 10. 첫 실행 작업 묶음

다음 구현 작업은 **P1-01 → P1-02 → P1-03/P1-04 → P1-05/P1-06 → P1-07** 순서다.
첫 실행에서 고정할 것은 아래 여섯 가지다.

- [ ] 보존 기준 후보의 실제 전체 서명·패키지 SHA·소유권·의존성 검사.
- [ ] 사용 가능한 네이티브 SDK·빌드 서버 공간·재현 도구 경로와 버전.
- [ ] 새 작업·후보·VM 이름과 기존 VM/디스크를 참조하지 않는지 여부.
- [ ] GNOME 기본 세션의 현재 동작과 성능 기준선.
- [ ] 라이트·다크 디자인 토큰과 확장 표시 범위.
- [ ] incident-ai의 실제 접속 주소·링크 규약 확인 여부.

관리자 회귀 검사의 기존 진입점은 다음과 같다. 이는 실행 방법이며 이 계획에서의
실행·통과 기록이 아니다. GTK 시험은 Linux 대상 환경과 실제 스냅샷이 필요하다.

```sh
python3 -B -m unittest discover -s tools -p test_kiki_admin.py -v
python3 -B -m unittest discover -s tools -p 'test_ki2ctl*.py'
make -C cmd/kiki-admin ui-test
cmd/kiki-admin/ui-test /path/to/snapshot.json /path/to/png-output
```
