# 빌드 웹 Git 소스 동기화

Git 서버의 변경을 빌드에 사용하되 기존 후보 작업본·설치기·패키지·ISO는
그대로 유지한다. Git 설정은 서버 관리자만 실행 환경에서 지정한다.

- `KIKI_GIT_URL=https://git.vlab.dustbox.kr/dustbox/kiki-os.git`
- `KIKI_GIT_BRANCH=stage3`
- 동등한 CLI 옵션: `--git-url`, `--git-branch`
- 저장 경로: `<artifact-root>/git/`의 bare 저장소·커밋별 tar 아카이브·SHA-256·이력
- 웹 화면: `/git`, 상태 API: `/api/git`, 가져오기: `POST /git/sync`

## 사용 순서

1. **Git 소스 동기화 → 최신 소스 가져오기**를 누른다.
2. 브랜치·커밋·변경 내용·아카이브 SHA-256을 확인한다.
3. 해당 커밋의 기본 검사·보안 검사 또는 **이 커밋의 패키지 빌드**를 실행한다.
4. 작업 상세에서 실제 사용한 커밋과 SHA-256을 확인한다.
5. 산출물 검증 후 새 릴리즈로 등록하고 기존 버전별 ISO 절차로 연결한다.

각 작업은 `jobs/<작업 ID>/source/`에 선택한 커밋을 복원한다. 소스 캐시도
`jobs/<작업 ID>/sources/`에 분리한다. 이후 가져오기가
일어나도 대기·실행 중인 작업과 재시도는 원래 커밋을 유지한다. 패키지 산출물은
기존 작업별 `packages/`, `repo/`, `work/` 경로를 사용한다. 기존 후보 명세와
Git 명세의 패키지 버전이 다를 수 있으므로 화면의 소스·커밋을 먼저 확인한다.

## 범위와 보존

서버는 Git에서 가져오기만 수행한다. 서버/개발 PC의 미커밋 작업을 자동으로
커밋·푸시하지 않는다. 네트워크 가져오기는 버튼으로 명시적으로 실행하며,
주기 동기화·webhook에 의한 자동 빌드·자동 릴리즈 승격은 이번 범위에 없다.

기존 작업본에는 `pull`, `reset`, `clean`을 실행하지 않는다. 동기화 실패 시
마지막으로 검증된 커밋과 아카이브를 유지하고 실패 상태를 표시한다. 같은
커밋의 기존 아카이브가 변조되면 다시 가져오기에서도 새 SHA로 승인하지 않는다.

Git 연동이 설정된 서버의 기본 `/package-build`와 `/kernel-build`는 **Git 최신 빌드**이다.
화면에는 마지막 확인한 명세를 보여주고, 작업 실행 직전에 HTTPS로 브랜치 최신을
가져온다. 실제 커밋·아카이브 SHA를 기록한 뒤 해당 커밋의 `ki2build.py`, 패키지
명세·설정·패치를 사용한다. 가져오기 실패 시 이전 작업본으로 대체하지 않는다.
실행 전후로 브랜치가 바뀌어도 이미 준비한 작업과 성공·실패한 빌드의 재시도는
실제로 고정했던 커밋을 유지한다. 소스를 고정하기 전 가져오기에 실패한 작업은
재시도 시 최신 가져오기를 다시 시도한다.

`/kernel-build`는 Git의 `linux` 명세를 사용한다. 화면에서 커널 버전·공식 소스 URL·
고정 SHA·설정 조각을 확인하며, 일반 패키지와 같은 독립된 작업별 경로에 커널
바이너리와 모듈을 묶은 `.ki2`를 만든다. 기존 커널 패키지를 덮어쓰지 않는다.
빌드·SHA 검사와 실제 VM 부팅·장치·로그인 검증은 별도 상태로 관리한다.

Git 화면의 **이 커밋의 …** 링크는 명시한 커밋으로 빌드하는 고정 모드이다.
Git을 설정하지 않은 기존 빌더와 명시적인 `source=preserved` 경로는 기존 작업본을
유지한다. 고정 입력에 의존하는 LLVM·Mesa
후보 파이프라인, 서명·publish·전체 release·ISO 파이프라인에는 Git 소스를
직접 적용하지 않는다. 완료된 ISO에 새 커밋 정보를 소급해서 붙이지 않는다.

## 권한과 실행 환경

운영자·관리자는 승인된 저장소의 소스를 가져오고 빌드를 요청할 수 있다.
조회자는 상태·이력을 볼 수 있고 변경 요청은 인증 계층에서 차단된다.
동기화와 빌드 요청 모두 기존 세션·Origin·CSRF 검증을 적용한다.

Git URL·브랜치는 웹 폼으로 받지 않는다. HTTPS URL에는 계정·토큰을 넣지 않는다.
Git에는 HTTPS를 통한 비대화형 읽기 접근이 필요하며, 공개 저장소에는 별도 자격 증명이 필요 없다.
Git SSH 전송과 SCP 형식의 Git 원격 주소는 허용하지 않는다. 실행 프로세스에도
HTTPS 프로토콜 허용 목록을 적용한다. 빌드 서버 관리용 SSH와 Git 전송은 별개이며,
Git에 SSH 키나 호스트의 SSH 폴더를 제공하지 않는다. 로컬 파일 전송은 임시 테스트
저장소에만 별도 허용되며 운영 CLI·웹에서는 활성화할 수 없다.

Git hooks·외부 프로토콜·로컬 파일 전송·하위 모듈 자동 가져오기를 금지한다.
1차 지원은 512 MiB 이하의 일반 파일·디렉터리 소스이다. 심볼릭 링크·서브모듈이
필요하면 별도 고정·검증 정책을 추가해야 한다. Git LFS 객체의 자동 다운로드도
지원하지 않는다. Git 커밋 식별자와 아카이브 SHA 확인은 공식 배포 서명 검증과 별개다.
기존 설치기처럼 Git에 포함하지 않는 로컬 런타임 번들을 요구하는 패키지는
번들 준비가 별도로 필요하며, 보존된 바이너리를 최신 소스 빌드로 바꿔 표시하지 않는다.

웹 제어 코드는 기존 검증된 운영 모듈을 사용하고, 새 Git 소스의 코드는 명시적으로
등록한 빌드 작업 안에서 실행한다. 빌더는 신뢰하는 개발자의 브랜치에만 연결한다.

## 검증

`tools/test_ki2git.py`는 실제 임시 Git 저장소로 가져오기·커밋 고정·미커밋 작업
보존·후속 커밋 이후 재시도·가져오기 실패·아카이브 변조·위험 경로·동시 요청을
검사한다. 기존 큐·웹 인증·테마 검사를 함께 실행한다. 배포 시 기존 서비스
설정만 백업하고 인증 DB는 복사하지 않는다. 이전 서비스 설정으로 복구할 수 있다.
