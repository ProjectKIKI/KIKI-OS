# 빌드 서버 외부 웹 연결

서버의 인증 웹은 SSH 터널용 `127.0.0.1:8092`와 VM 주소 `10.250.254.229:8092`를 하나의 컨테이너 HTTP 8092로 연결한다. 최신 구성은 [일반 HTTP 웹 서비스](kiki-build-web-http-20261025.ko.md)이며 외부 프록시 전용 옵션·수신기·전달 헤더 처리를 제거했다. 로그인·HTTPS Origin·Secure 쿠키·CSRF 검사는 유지한다.

아래 항목은 최초의 엄격한 프록시 연동 구성 기록이다.

- 접속 출발지: Terminal Lab 프록시 `10.0.161.214`.
- Host: `kios-build.lab.terminal-lab.kr`.
- HTTPS 전달 정보: `X-Forwarded-Proto: https`.
- 로그인 쿠키: `HttpOnly`, `SameSite=Strict`, `Secure`.
- 변경 요청: 외부 HTTPS Origin과 CSRF 토큰을 검사한 뒤 고정된 내부 Host/Origin으로 전달한다.

프록시가 HTTP로 받은 요청은 공개 HTTPS 주소로 리디렉션한다. 등록되지 않은 출발지의 HTTPS 헤더 위장은 거절한다. 8091 패키지 컴파일러와 8094 버전·ISO 작업자는 루프백에만 남긴다. TLS 인증서는 외부 프록시에서 처리하며 서버의 8092 연결은 내부 HTTP다.

서버의 사용자 systemd 설정은 원래 `kiki-build-auth.service`를 보존하고 `kiki-build-auth.service.d/https-ingress.conf`에서 네트워크와 수신 설정을 적용한다. 인증 웹은 이후 전용 이미지와 명시적인 8092 포트 매핑으로 이관했다. 상세 구성은 [인증 웹 컨테이너 기록](kiki-build-auth-container-20261025.ko.md)을 참고한다. 원래 관리자 계정·비밀번호·인증 DB는 그대로 사용한다.

## 보안그룹 구성

빌드 서버 전용 그룹은 수신 TCP 22·8092를 `10.0.161.214/32`에서 허용한다. 22는 기존 외부 SSH 41816 포워딩의 서버 측 포트다. IPv4 송신은 소스 다운로드·DNS·패키지 빌드에 사용한다. VM에 80·443·8091·8094 인바운드를 추가할 필요는 없다.

2026-10-25 점검 시 VM에는 `ai-incident`만 연결되어 있었고, 새 그룹 생성은 보안그룹 규칙 할당량 오류로 실패했다. 사용자 승인 후 미사용 `terminal-lab-service-8092`를 삭제하고 `kiki-build-web-20261025`를 생성했다. 기본 IPv6 송신 규칙을 제거하고 IPv4 송신·프록시 출발지의 TCP 22·8092 수신, 총 3개 규칙을 유지한다. 새 그룹을 빌드 서버에 연결하고 `ai-incident`는 해당 VM에서만 해제했다. 해제 후 외부 SSH 41816으로 새 세션의 로그인 성공을 확인했다. 다른 VM의 그룹은 변경하지 않았다.

`kios-build.lab.terminal-lab.kr`은 HTTP 백엔드 `10.250.254.229:8092`로 등록됐다. 공개 HTTPS의 TLS 연결은 성공하지만 HTTP 응답은 시간 초과 상태다. 외부 요청 중 VM ens3에서 35초간 TCP 8092 패킷 메타데이터를 확인했으며 수신 패킷은 없었다. 웹 프록시의 실제 출발지 IP 또는 프록시 상위 경로를 확인해야 한다. SSH 프록시 출발지는 `10.0.161.214`로 확인됐으나 웹 프록시도 같은 주소인지는 아직 검증하지 못했다. 공개 HTTPS 로그인 성공을 확인하기 전까지 외부 접속 복구 완료로 판단하지 않는다.

인증·컴파일·버전 작업자 서비스는 모두 실행 중이며 루프백 로그인과 버전 API는 각각 HTTP 200이다. 서버 내부 직접 요청에서 신뢰 프록시 출발지를 위장한 접근은 HTTP 403으로 차단된다. 이번 네트워크 작업은 기존 설치기·패키지·ISO·인증 계정을 변경하지 않았다.

## 버전 목록 복구

버전·ISO 작업자의 `catalog.json`이 0바이트여서 서비스가 재시작을 반복했다. 보관 객체·기존 파일 명세·서명된 스냅샷·완료 빌드 기록을 검증해 목록을 재구성했다. 원인 자체는 확정하지 않았다.

복구는 보관 객체 291개의 SHA와 기존 스냅샷의 인덱스·메타데이터 SHA 및 서명을 확인한다. 바이너리 185개·소스와 관련 파일 106개·스냅샷 4개를 연결하며, 손상 목록은 별도로 보존한다. 기존 설치기·패키지·소스·ISO·스냅샷을 삭제하거나 재빌드하지 않는다.

JSON 저장에는 임시 파일의 flush·fsync, 원자 교체, 부모 디렉터리 fsync를 적용한다. 정상 목록 백업을 함께 유지하고, 변경이 없는 동기화는 목록을 다시 쓰지 않는다. 시작 시 기본 목록이 손상되면 스냅샷 참조가 유효한 정상 백업에서 복구하고 손상 파일을 보존한다.

수동 복구 도구 `tools/ki2release_recover.py`는 작업자 서비스를 중지한 상태에서 전용 잠금을 획득해 사용한다. 실제 서버 경로와 읽기 전용 입력 마운트가 맞는 후보 컨테이너 안에서 실행한다.
