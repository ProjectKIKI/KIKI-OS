# 외부 빌드 웹 로그인 복구

2026-10-25, 사용자 승인에 따라 외부 80번을 기존 인증 컨테이너로 전달했다. 실제 외부 HTTPS와 브라우저에서 로그인 화면을 확인했다.

현재 운영 주소: **https://cloud-7-3b778824-09936d.lab.terminal-lab.kr/login**

## 8092 비교 결과

사용자는 빌드 서버 서비스 중지를 승인했다. 인증 컨테이너만 잠시 중지하고 호스트의 Python 표준 HTTP 서버를 `0.0.0.0:8092`에 실행해 같은 도메인의 `/healthz`를 비교했다. 임시 서버에는 인증 DB·빌드 자료를 연결하지 않았으며 `/`·`/healthz` 이외 경로는 404였다.

| 검사 | 결과 |
|---|---|
| 기존 인증 컨테이너, VM 직접 8092 | 200 |
| 기존 인증 컨테이너, 외부 8092 | 503 |
| 컨테이너 없는 단순 HTTP 서버, VM 직접 8092 | 200, 점검 문구 일치 |
| 같은 단순 서버, 외부 HTTP·HTTPS 8092 | 모두 약 20초 후 503 |
| 동시에 검사한 외부 Apache 80 | 200 |

VM ens3 캡처에서는 80번 요청과 응답이 보였고, 들어오는 8092 패킷 행은 없었다. 캡처 통계는 captured 10 / received by filter 12 / dropped 0이었다. 단순 서버의 요청 기록에는 VM 내부 점검만 있었다. 임시 서버 시작은 19:53:34 KST, 인증 복구 완료는 19:54:28 KST로 약 54초였다. 복구 후 기존 로그인 200을 확인했다.

이 결과는 외부 8092의 503을 빌드 웹 코드나 rootless 컨테이너 포트 게시 문제만으로 설명하기 어렵다는 근거다. 관리형 프록시의 실제 backend 연결과 게스트 앞단의 네트워크 차단 중 어디가 원인인지는 아직 확정하지 못했다. 직접 8092 경로를 고쳤다고 판단하지 않는다.

## 함께 수정한 웹 설정

현재 VM에는 `cloud-7-3b778824-b86812.lab.terminal-lab.kr → 8092`가 등록돼 있었다. 기존 `kios-build` 연결은 사용자 콘솔 목록에서 사라졌고 외부 요청도 421이었다. 인증 앱은 이전 `kios-build` Host만 허용하고 있어, 새 8092 Host의 `/login`은 VM 직접 요청에서도 400이었다.

인증 서비스의 허용 HTTPS 주소에 새 8092 주소와 실제 사용할 80번 주소를 추가했다. 기존 SSH 터널 주소와 이전 주소도 유지했다. 이후 새 주소로 VM 직접 로그인 200, 미인증 API 401, 공개 주소 Secure 쿠키를 확인했다. 비밀번호·계정·인증 DB 사본은 생성하거나 변경하지 않았다. 정상적인 익명 로그인 화면 조회는 앱의 기존 방식대로 사전 세션을 생성한다.

## 승인한 80번 운영 구성

외부 HTTPS는 터미널랩에서 종료되고, VM의 80번 요청은 OS nftables가 기존 8092 수신기로 전달한다. 기존 인증 컨테이너·내부 빌드 API·버전 작업자를 재사용한다. Apache의 파일·설정·서비스는 보존했고 외부 80번 화면은 빌드 웹으로 전환됐다. VM 내부의 Apache 80번 점검은 계속 가능하다.

- 전용 nftables 파일: `/etc/nftables/kiki-build-web.nft`.
- 전용 테이블: `ip kiki_build_web`.
- 범위: `ens3`, 목적지 `10.250.254.229`, TCP 80 → 8092.
- 서비스: `/etc/systemd/system/kiki-build-web-portmap.service`.
- 인증 설정: 기존 사용자 서비스의 `web-http.conf`에 HTTPS origin 추가.
- 자동 시작 `enabled`, 실행 상태 `active`, 매핑 서비스 재시작 후 외부 재검증 통과.
- 실제 VM 재부팅은 이번 점검에서 수행하지 않았다.

SELinux는 점검 도중 임시 Permissive 상태였고 영구 설정은 `enforcing`이었다. 런타임도 Enforcing으로 복구한 뒤 외부 로그인과 API 차단을 다시 검증했다. SELinux 보호를 해제한 채 운영하지 않는다.

## 최종 검증과 보존

- 외부 HTTPS `/login`: 200, 한국어 로그인 폼, Secure·HttpOnly·SameSite=Strict 쿠키.
- 외부 미인증 `/api/jobs`, `/api/releases`: 각각 401.
- 관리자 비밀번호 입력이나 실제 관리자 로그인은 수행하지 않았다.
- 빌드 컨테이너 `f2799e4e3c8f`, 버전 작업자 `792d27c59803`: 계속 실행, 변경 없음.
- 인증 컨테이너는 설정 적용을 위해 재시작했다. 기존 상태 볼륨을 그대로 사용했다.
- 기존 설치기·원본 패키지·서버 작업본을 삭제하거나 대체하지 않았다. 최종 SHA 결과는 `preservation-final.json`을 기준으로 한다.

구성 원본은 로컬 `deploy/nftables/kiki-build-web.nft`, `deploy/systemd/kiki-build-web-portmap.service`에 있다. 서버 진단·설정·검증 기록은 후보의 `port8092-recheck-20261025/`에 보관한다. 다운로드 보고서는 인증 DB·쿠키 값·세션 토큰을 포함하지 않는다.

## 복구

`sudo systemctl disable --now kiki-build-web-portmap.service`로 이 전용 포트 매핑을 해제하면 외부 80번은 보존한 Apache로 돌아간다. 이 작업은 다른 nftables 테이블을 건드리지 않는다. 현재 도메인 로그인을 유지하려면 인증 서비스의 HTTPS 주소 설정은 유지한다. 인증 설정 자체를 되돌릴 때는 후보의 `web-http.before.conf`와 이후 정상화 설정을 대조해 필요한 주소만 되돌리고 인증 서비스만 다시 시작한다. 인증 DB는 복원하거나 덮어쓰지 않는다.

자동 승인 검토가 임시 인증 중단과 80번 영구 전환을 각각 보류했으며, 두 작업은 사용자의 명시적 승인 후 수행했다. 인증 DB 추가 백업은 거절돼 복제하지 않았다.
