2026-10-28 빌드 서버에 자동 배포와 외부 HTTP·HTTPS 읽기 전용 공개를 적용했다.
SSH·rsync 방식은 이 문서에서 검토만 했으며, 별도 계정·키·rsync 데몬은 구성하지 않았다.

CLI 등록 예시(해당 채널의 신뢰 공개키를 먼저 `/etc/ki2/trust/build-candidate.ed25519.pub`에 배치):


## 자동 배포 흐름

1. 빌드 콘솔이 Git 커밋에 고정한 소스로 개별 패키지를 빌드한다.
2. 버전 작업자가 완료 상태인 작업만 수집한다. 현재 작업 경로와 이전 작업 경로를 모두 확인한다.
3. 패키지 SHA·파일 명세·Git 레시피 지문을 검증한다.
4. 현재 자동 배포 기준에 새 패키지를 병합하고 의존성 폐쇄성을 검사한다.
5. 기존 서버 후보키로 Ed25519 서명 스냅샷을 생성한다. `build-<작업 ID의 SHA-256 앞 24자리>`로 이름을 고정한다.
6. 독립 저장소 서비스가 15초 간격으로 완료된 스냅샷을 발견하고 서명·전체 패키지 해시를 재검증한다.
7. 임시 디렉터리를 원자적으로 게시한 뒤 후보 채널을 갱신한다. 이전 버전과 패키지 경로는 보존한다.

작업자 동기화 주기와 검증 시간이 추가되므로, 빌드 종료 시점부터 공개까지 정확히 15초를 보장하지 않는다.
검증 중 실패하면 기존 채널을 유지한다. 실패·실행 중 빌드와 `.pending-*` 디렉터리는 게시하지 않는다.
버전 하락과 동일 패키지 파일명의 바이트 변경은 자동 승격을 거부한다. 내용이 달라졌으면 레시피의
`release` 번호를 올려 새 파일명으로 빌드해야 한다. 거부 사유는 인증된 `/versions` 화면에 표시한다.

빌드 성공과 배포 성공은 별도 상태다. 파일 검사가 통과해도 의존성·서명·게시 조건에 실패할 수 있다.
자동 배포의 검증 범위는 빌드 산출물·의존성·서명이며, 런타임·새 설치·부팅 검증은 별도다.

## HTTP 경계와 운영 경로

공개 경로는 `/ki2/` 하나이며 GET·HEAD만 허용한다. 전용 서비스는 루프백 `127.0.0.1:8097`에서 실행한다.
기존 인증 앞단이 해당 접두사만 전달하며 Cookie·Authorization·사용자 입력 Origin은 전달하지 않는다.
작업자 API·로그·계정·서명 개인키·임의 파일·디렉터리 목록은 공개 대상에 포함하지 않는다.
기존 관리 경로는 로그인·역할·CSRF 검사를 유지한다. 방화벽이나 외부 포트 매핑은 변경하지 않았다.

| 항목 | 서버 경로/서비스 |
|---|---|
| 저장소 서비스 | `kiki-repository.service` (systemd 사용자 서비스, enabled) |
| 게시 저장소 | `/build-kikios/kiki-build/candidates/mesa-native-20261023/public-repository` |
| 게시 설정 | 같은 기본 디렉터리의 `repository-deploy-20261028/config.json` |
| 게시 결과/오류 | `public-repository/state.json`, `public-repository/last-scan.json` |
| 자동 서명 정책 | `release-store/repository-auto-publish.json` |
| 작업자 추가 설정 | `~/.config/systemd/user/kiki-release-worker.service.d/zz-repository-auto-publish.conf` |
| 배포/복구 기록 | `repository-deploy-20261028/deployment.json` |

`lab` 사용자의 linger가 활성화되어 있고 저장소 서비스는 사용자 기본 target에 등록했다.
실제 서버 재부팅 검증은 수행하지 않았다. 이전 SSH 전용 임시 서비스의 24시간 제한은 새 서비스에 적용되지 않는다.
새 서비스는 명시적으로 중지할 때까지 운영한다.

같은 파일 시스템의 패키지는 하드링크로 재사용한다. 검증 후 원본 파일을 덮어쓰지 않는 것이 계약이다.
교체·크기·수정 시간이 바뀐 파일은 HTTP 503으로 차단하고 재검증을 요구한다.
다른 파일 시스템은 복사로 대체한다. 현재 자동 삭제·보관 개수 제한은 없으며, 최종 확인 시 빌드 볼륨 여유는 약 61GiB였다.
채널 갱신 순간에 메타데이터와 인덱스의 세대가 엇갈리면 클라이언트 해시 검사가 실패할 수 있다.
다시 `update`하거나 버전 고정 URL을 사용한다. 서명·해시 검사를 생략해서 해결하지 않는다.

## 검증 결과

### 패키지 출처 화면

각 채널의 `/sources.html`에서 패키지 이름·출처 검색과 출처 종류 필터를 제공한다.
`/sources.json`에는 같은 출처 정보를 기계가 읽을 수 있는 형태로 제공한다.
원본 HTTPS 주소·배포 호스트, SHA-256 확인된 보관 소스, 로컬 빌드 입력 경로,
빌드 입력 Git 주소·커밋을 표시한다. 외부 라이브러리의 원본 주소와 KIKI 레시피 Git은 별도로 표시한다.

출처는 해당 바이너리 SHA-256에 연결된 빌드 기록에서 가져온다. 이름이 같다는 이유로 다른 버전의 출처를 추정하지 않는다.
미기록 항목은 `출처 확인 필요`, 커밋이 없는 로컬 입력은 `커밋 미기록`으로 표시한다.
관리자 앱과 새 KI2 CLI의 로컬 경로는 검증한 바이너리 해시에 고정한 별도 기록을 사용한다.
이 출처 JSON은 안내 정보이며 기존 서명 메타데이터의 일부라고 표시하지 않는다.

224개 후보의 패키지 해시·내장 레시피 지문과 보존된 레시피를 모두 대조했다.
외부 원본 210개, 자체 소스·설정 12개, 보존된 외부 파일 포함 2개로 구분하며,
미연결 항목은 0개다. 외부 원본의 고유 입력 파일 201개는 실제 파일 SHA-256도 대조했다.
세부 범위와 인스톨러·폰트 묶음의 한계는 [감사 기록](package-source-audit-20261028.ko.md)에 명시했다.
`provenance.audit_file`과 `provenance.audit_objects`로 과거 빌드의 고정 매핑·추가 보관본을 연결한다.
매핑은 정확한 패키지 해시와 이름·버전·release가 모두 일치할 때만 사용한다.

보관본 공개는 패키지의 외부 원본 주소·소스 해시와 연결되고 서버에서 해시를 검사한 압축파일 및 공개 CA 입력 PEM만 허용한다.
서버 절대 경로, 인증값을 포함한 URL, 임의 객체 파일은 공개하지 않는다.
이 기능은 출처 조회이며 새 버전 주기적 검사·알림은 아직 구현하지 않았다.

## 중지·복구

자동 서명만 중지하려면 `release-store/repository-auto-publish.json`의 `enabled`를 false로 설정한다.
이미 게시한 버전과 HTTP 서비스는 유지된다. HTTP 게시·조회까지 중지하려면:

```sh
systemctl --user stop kiki-repository.service
```

이 경우 `/ki2/`는 502가 되지만 기존 관리 경로는 독립적으로 동작한다.
인증 앞단을 배포 전 이미지로 되돌리면 `/ki2/`도 기존의 로그인 경로로 돌아간다.
이 배포의 원본 이미지 ID와 재사용 태그는 서버의 `deployment.json`에 기록했다.
복구 시 해당 원본 ID로 태그를 되돌리고 `kiki-build-auth`만 재시작한다.
작업자 원복은 `zz-repository-auto-publish.conf`를 비활성화한 뒤 daemon-reload와 작업자 재시작으로 수행한다.
빌드·ISO 작업이 실행 중인지 먼저 확인한다. 인증 DB·비밀번호·서명 개인키를 복원하거나 복제할 필요는 없다.

## SSH·rsync 방식 검토 (구성하지 않음)

권장 구성은 **빌드 서버에서 저장소로 올릴 때 SSH 또는 rsync over SSH, OS 클라이언트에 배포할 때 HTTPS**다.
현재 빌드와 저장소가 같은 서버라면 전송 없이 검증된 로컬 파일을 게시하는 구성이 가장 단순하다.

| 방식 | 적합한 용도 | 이 저장소에 적용할 때 |
|---|---|---|
| HTTPS | 다수 OS 클라이언트의 패키지 조회·설치 | 기존 KI2·GUI와 호환, 전송 암호화·서명 검사 유지 |
| HTTP + Ed25519 | 임시 공개·신뢰 네트워크 | KI2 지원, 패키지 진위·무결성 검증 가능, 전송 내용은 암호화하지 않음 |
| SSH/SFTP/SCP | 운영자 또는 CI의 인증된 업로드 | 계정·키·호스트키 관리 필요, KI2의 `ssh://` 직접 저장소로는 현재 미지원 |
| rsync over SSH | 다른 서버로 증분 미러·대용량 동기화 | 기존 SSH 포트 사용 가능, 전송 후 서버 검증·원자적 게시 필요 |
| rsync 데몬 | 별도 관리하는 읽기 전용 미러 | 별도 노출·접근 제어·암호화 계층 검토 필요, 이번 구성에서는 이점이 작음 |

KI2 클라이언트는 HTTP(S) 또는 `file://` 저장소를 사용한다. SSH·rsync로 미리 받은 로컬 미러를
`file://`로 등록할 수 있지만, 자동 동기화·중단 복구·원자적 전환을 별도로 구현해야 한다.
패키지를 설치하는 모든 OS에 SSH 배포용 키를 나눠주는 운영 비용도 생긴다.

나중에 저장소를 다른 서버로 분리한다면 전용 배포 계정과 제한된 키로 staging 디렉터리에만 쓰게 하고,
수신 서버에서 서명·해시 검증을 마친 새 버전을 원자적으로 게시하는 방식을 권장한다.
실제 공개 디렉터리에 바로 동기화하거나 live 디렉터리에 `rsync --delete`를 적용하지 않는다.
`.ki2`는 압축된 아카이브이므로 rsync 추가 압축의 효과는 실측해 판단한다.

근거: [rsync 공식 개요](https://www.samba.org/ftp/rsync/README.html)는 SSH 사용을 권장하며,
[공식 매뉴얼](https://www.samba.org/ftp/rsync/rsync.1)은 원격 셸 전송과 데몬 전송을 구분한다.
설치된 rsync 버전·SSH 제한 계정 구성·성능은 이번에 검증하지 않았다.
